# 소유자 인증·클라우드 동기화 연결 설계

상태: **설계안**, 작성 2026-11-17. 현재 앱은 v0.9.0 로컬 저장/파일 왕복 기반이다. 이 문서가 로그인·서버·자동 동기화의 구현 완료나 활성화를 뜻하지 않는다. 클라우드 프로젝트 생성·운영 DB 변경·실제 메모 업로드는 수행하지 않았다.

## 소유자 인증의 의미

인증은 로그인한 사람이 누구인지 확인하는 것이고, 인가는 그 사람이 접근할 수 있는 메모·사진만 허용하는 것이다. 메모별 색상·글꼴·배치를 설정하는 개인화와 구분한다. PC·웹·모바일에서 같은 계정으로 로그인하면 같은 메모에 접근하고, 다른 계정은 메모 ID나 이미지 주소를 알아도 접근할 수 없어야 한다.

이 인증은 클라우드 접근 제어다. 기존 Windows 로컬 SQLite 파일을 암호화하거나 앱 자체를 잠그는 기능은 아니다. 로그인하지 않았거나 서버가 중단되어도 기존 로컬 메모 열기·수정·저장·백업은 계속 가능해야 한다.

## 권장 구성과 경계

첫 연결안은 **앱 전용 Supabase 프로젝트의 Auth + Postgres + 비공개 Storage**이다. 이미 운영하는 다른 서비스의 계정·테이블·버킷과 분리한다. 제공업체와 연동 규격은 배포 전에 비용·약관·대상 프로젝트를 확인하며, 특정 요금제를 전제로 하지 않는다. 현재 계정 연결 상태는 읽기만 확인했다.

| 역할 | 설계 |
|---|---|
| 로그인 | 관리형 Auth의 이메일 인증코드부터. 소셜 로그인은 다음 확장 |
| 사용자 구분 | 검증된 세션의 사용자 UUID. 클라이언트가 보낸 이메일/owner_id를 신뢰하지 않음 |
| 메모 | Postgres의 소유자별 JSON 문서 + 원격 리비전 |
| 이미지 | 비공개 버킷의 owner UUID/해시 경로, 원본은 불변 |
| 접근 제어 | 사용자 JWT 검증, DB RLS, Storage 정책을 함께 적용 |
| PC | 현재 로컬 SQLite + 인증정보 보호 저장소 + 동기화 대기열 |
| 웹 | 현재 갤러리에 로그인과 API 연결. 파일 왕복 기능도 유지 |
| 모바일 | 이후 같은 API/문서 계약을 사용. 화면과 위젯은 별도 구현 |

공식 문서상 RLS는 사용자별 행 접근을 제한할 수 있고, Storage의 소유자 표기만으로 접근 제어가 완성되지는 않는다. **메모와 첨부 모두 별도 소유권 정책을 검사**한다.

- [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)
- [Storage ownership](https://supabase.com/docs/guides/storage/security/ownership)
- [Private buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals)

## 로그인과 계정 연결

1. 기존 앱은 로컬 모드로 시작한다. 로그인 실패를 앱 종료·메모 차단 사유로 사용하지 않는다.
2. 첫 버전은 미리 허용한 소유자 계정만 접속시킨다. 공개 회원가입은 제공하지 않고 이메일 인증 요청이 새 사용자를 임의 생성하지 않도록 설정한다.
3. 이메일 인증코드를 확인하면 Auth가 발급한 세션을 사용한다. 앱에서 비밀번호를 따로 수집·저장하지 않는다. 소셜 로그인 추가 시 시스템 브라우저/PKCE를 사용하며 코드 검증과 콜백 검증을 구현한다.
4. Windows 갱신 토큰은 현재 Windows 사용자에 묶인 DPAPI로 보호해 앱 데이터 폴더에 저장한다. 액세스 토큰은 메모리에 두고 로그·오류·URL에 기록하지 않는다. 관리자/service role 키는 exe·웹 JS에 넣지 않는다.
5. 웹은 짧은 세션을 메모리에 두는 방식부터 검증한다. 브라우저를 닫거나 새로 여는 세션의 지속성을 원하면 서버가 관리하는 HttpOnly/Secure/SameSite 쿠키 흐름을 별도 구현한다. 장기 토큰을 일반 작업 파일에 넣지 않는다.
6. 최초 연결 화면에서 계정과 동기화할 메모 개수·첨부 용량·대상을 보여주고 사용자가 선택한 범위만 계정에 연결한다. 로그인만으로 기존 모든 메모를 전송하지 않는다.
7. 계정이 바뀌면 기존 연결을 새 계정으로 자동 이전하지 않는다. 계정별 로컬 프로필을 분리하고, 아직 동기화되지 않은 변경을 먼저 보존한다. 기존 무계정 프로필을 다른 계정에 중복 연결할 때도 명시적 선택을 요구한다.
8. 로그아웃하면 네트워크 작업을 취소하고 토큰을 제거한다. 로컬 메모는 삭제하지 않는다. 다시 연결 시 같은 계정인지 검증한다.

[PKCE 공식 흐름](https://supabase.com/docs/guides/auth/sessions/pkce-flow). 현재 .NET Framework4.8의 대상 OS에서 TLS 연결을 확인한 뒤 통합한다. 최근 TLS 변경은 [공식 변경 기록](https://supabase.com/changelog/cbc-tls-ciphers-deprecated)을 확인하며 구형 TLS로 우회하지 않는다.

## 데이터 분리

| 데이터 | 위치/정책 |
|---|---|
| 문서 ID·종이 크기·배경·요소·텍스트·필기 | 동기화 대상. 현재 중립 JSON 형식 유지 |
| 이미지 원본·체크섬·픽셀 크기 | 해시별 비공개 첨부. 메모와 연계한 소유권 검사 |
| 창 위치·크기·모니터·배율·상단 도구 표시·펜 설정 | 기본적으로 기기별 로컬 보기 설정 |
| 창 전체 불투명도 | 현재 NoteView에 있으므로 기기별 유지. 문서 배경색과 구분 |
| 휴지통/복구 | 삭제 표식을 문서 변경으로 동기화. 자동 영구 삭제는 하지 않음 |
| 계정/세션 | 별도 보호 저장. 문서 JSON·ZIP·웹 작업 파일에 넣지 않음 |

문서의 기존 Revision과 **원격 리비전**은 별개다. 서버가 부여한 remote_revision, 동기화 기준 해시, 계정/문서 연결 정보를 로컬 보조 테이블에 두고 기존 메모의 ID를 바꾸지 않는다. 서버 내용 해시는 원문 JSON 바이트의 SHA-256을 사용한다. 문서 원문을 전송·보관하고 임의 재직렬화로 해시를 바꾸지 않는다. 웹 수정은 기존 텍스트 패치 계약을 발전시켜 서버에서 검증·직렬화한다.

## 동기화 동작

- 1차 연결은 **수동 동기화 버튼**부터 검증한다. 이후 로컬 저장 확정·앱 재개·네트워크 복구 이벤트에 배치 전송을 연결한다. 펜 이동이나 이미지 슬라이더 매 순간 전송하지 않는다.
- 문서 저장과 대기열 기록은 같은 SQLite 트랜잭션으로 처리한다. 네트워크 실패로 로컬 저장을 롤백하지 않는다.
- 각 작업은 operation_id로 식별하고 재시도에도 같은 ID를 사용한다. 서버는 같은 요청을 중복 적용하지 않는다. 동일 ID에 다른 요청 내용은 거절한다.
- 첨부를 먼저 올리고 해시·크기를 검증한 뒤 해당 첨부를 참조하는 문서를 반영한다. 파일은 해시별로 유지하고 원본을 덮어쓰지 않는다.
- 문서 갱신은 서버의 기대 리비전·기준 해시가 현재 값과 일치할 때만 반영한다. PC/웹이 동시에 수정한 경우409 충돌로 중단하고 양쪽 사본을 보존한다. 자동으로 최신 시간의 내용을 승자로 정하지 않는다.
- 내려받은 내용도 검증 후 트랜잭션으로 적용한다. 로컬에 미전송 변경이 있으면 그대로 덮어쓰지 않는다. 충돌 사본·비교 후 적용을 제공한다.
- 인증 만료는 세션을 갱신하고 한 번 재시도한다. 갱신 실패 시 동기화를 멈추고 재로그인을 표시하되 로컬 편집은 계속한다.
- 일시적 오류는 제한된 지수 백오프와 취소 가능한 재시도를 사용한다. 장기 오프라인에서는 유휴 폴링 대신 네트워크 복구/사용자 동작을 기다린다.
- 동기화 상태는 로컬 저장 완료, 업로드 대기, 동기화 완료, 충돌, 로그인 필요로 구분한다. 로컬 저장 완료를 클라우드 완료로 표시하지 않는다.

## 서버가 보장할 규칙

- 요청의 소유자는 검증된 세션에서 가져온다. 요청 본문의 user_id를 소유권 근거로 쓰지 않는다.
- 모든 메모 조회·변경·목록·첨부 요청에 소유권 조건을 적용한다. DB에는 RLS를 적용하고 UPDATE의 기존 행/변경 후 행에 모두 owner 검사를 둔다.
- 공개/익명 접근은 메모·첨부 모두 거절한다. 다른 소유자의 존재 여부가 드러나지 않게404로 처리한다.
- 원격 순번은 서버가 관리한다. 서버별 문서 단위 CAS는 같은 트랜잭션에서 비교하고 변경한다. 변경 스트림 커서는 단순 sequence 최대값으로 만들지 않고, 커밋 순서를 보장하는 계정별 직렬화 또는 검증된 CDC 방식을 선택한다. 이를 검증하기 전에는 전체 문서 리비전 목록 대조를 사용한다.
- 이미지 bucket은 private이며 소유자 경로와 실제 메타데이터의 소유권을 모두 검증한다. URL을 아는 것만으로 접근할 수 없어야 한다.
- 임시 서명 URL을 사용하면 짧은 유효기간을 두고 로그아웃 즉시 만료된다고 가정하지 않는다. 첫 단계는 인증된 다운로드를 우선한다.
- 동일 이미지의 전역 존재 여부를 다른 계정에 공개하지 않는다. 중복 제거는 계정 범위다.
- 휴지통·실행 취소·충돌·업로드 대기에서 참조하는 첨부는 정리 대상에서 제외한다. 최초 버전에서는 자동 첨부 영구 삭제를 구현하지 않는다.

## 구현 순서와 완료 기준

1. 전용 개발 프로젝트 및 테스트 계정2개 준비, 비용/위치/로그인 방식을 확정. 기존 서비스와 분리.
2. DB·첨부 정책을 먼저 구현하고 미로그인·타인 접근 거절을 실제 테스트 계정으로 확인.
3. 데스크톱 로그인/로그아웃·토큰 보호·만료 갱신을 검증. 이 단계만으로 기존 메모를 업로드하지 않음.
4. 사용자가 선택한 인공 메모의 최초 업로드·복원을 검증. 문서/이미지 해시 일치 확인.
5. 대기열·재시도·중복 억제·충돌 사본·휴지통 복원을 구현.
6. 웹 로그인·갤러리 API 연결·글 수정 반영을 검증. 아직 없는 웹 도형 이동/그리기는 별도 단계.
7. 테스트 계정 두 개와 기기 두 개로 접근 분리·중단 후 재개·계정 전환 검증 후 실사용 연결.

현재는 위 구성·경계·흐름을 정리한 설계 단계이며, 실제 DB 권한/토큰/계정 분리 시험을 통과했다고 주장하지 않는다. 상세 API와 인수 조건은 [API 계약](AUTH_SYNC_API.md)을 따른다.
