# 인증·동기화 API 계약 초안 v1

상태: 설계용. 아직 서버나 클라이언트에 연결되지 않음. 기존 오프라인 웹 작업 파일 v1을 그대로 HTTP로 업로드하는 계약은 아니다. 실제 구현에서 제공업체의 최신 API와 검증을 반영한다.

## 요청/응답

모든 메모/첨부 요청은 HTTPS, 검증된 사용자 세션이 필요하다. PC는 Bearer 액세스 토큰, 웹 세션 유지 기능을 도입하면 동일 출처의 보안 쿠키/BFF 흐름을 별도 사용한다. URL/로그/문서에 토큰을 넣지 않는다.

| 경로 | 동작 | 주요 값 |
|---|---|---|
| GET /v1/session | 검증된 현재 사용자·계정 연결 확인 | 서버 확인한 user UUID, 지원 문서 스키마 |
| GET /v1/notes/versions | 내 문서 ID/원격 리비전/해시/휴지통 목록, 페이지 단위 | 페이지 토큰, next_page; 변경 스트림과 구분 |
| GET /v1/notes/{id} | 소유 문서 원문 읽기 | raw_document, remote_revision, content_hash |
| POST /v1/operations | 생성/갱신/휴지통/복원 | operation_id, note_id, expected_remote_revision, expected_hash, base64 원문 또는 타입별 패치 |
| GET /v1/operations/{id} | 재시도 후 적용 결과 확인 | 같은 소유자의 작업만 조회 |
| POST /v1/assets/reserve | 내 계정 범위 첨부 준비 | hash, bytes, MIME, 픽셀 크기 |
| PUT /v1/assets/{hash} | 불변 파일 업로드 | 원본 바이트, 서버 검증 전 미완료 상태 |
| GET /v1/assets/{hash} | 인증된 파일 다운로드 | 소유자 검사 및 해시 검증 |

문서 생성은 기대 리비전0, 기준 해시 없음으로 구분한다. 서버는 로컬 Revision을 원격 리비전으로 사용하지 않는다. 문서 본문 스키마는 현재1~4, 요소/좌표/첨부 제한은 데스크톱 검증 규칙 이상으로 느슨하게 허용하지 않는다. 20MiB 이미지 한도는 현재 앱과 맞추되 저장소·업로드 제한은 실제 설정에서 별도 확인한다.

`operation_id`는 계정 내에서 유일하고 재시도 동안 유지한다. 서버는 요청 해시와 응답을 함께 보관한다. 같은 ID/같은 요청은 기존 응답, 같은 ID/다른 요청은409. 소유자를 operation_id 조회에도 반드시 결합한다. 성공 응답에는 적용된 원격 리비전·문서 해시가 포함된다.

## 최소 서버 테이블 개념

| 개념 | 핵심 필드/불변 조건 |
|---|---|
| notes | owner_id + note_id 복합 키, remote_revision, raw_document, hash, deleted_at |
| assets | owner_id + sha256 복합 키, bytes/MIME/크기, private object path, verified |
| note_assets | 같은 소유자 메모/첨부만 연결, 업로드 검증 완료 전 문서에 연결 금지 |
| operation_receipts | owner_id + operation_id 복합 키, request_hash, 결과, 적용 트랜잭션과 원자적 저장 |
| 로컬 sync_binding | 계정·프로젝트·로컬 문서 매핑, last_synced_revision/hash |
| 로컬 outbox | operation_id, 기준 리비전/해시, 변경 스냅샷, 상태, 재시도 메타데이터 |

사용자 UUID를 메모 본문에 삽입해 현재 문서 형식을 변경하지 않는다. 로컬 계정 전환·프로젝트 전환 때 연결 정보를 검증한다. 창 보기 설정은 업로드하지 않는다.

## 상태와 오류

| 상황 | 처리 |
|---|---|
| 401 인증 누락/만료 | 로컬 저장 유지, 세션 갱신 실패 시 로그인 필요 |
| 404 미소유/없는 문서 | 자료 존재 여부를 노출하지 않음 |
| 409 기준 불일치/동일 작업 ID의 다른 요청 | 자동 덮어쓰기 금지, 충돌 사본 보존 |
| 413 파일/본문 한도 초과 | 해당 작업 중단, 원본 유지 |
| 422 스키마/첨부 검증 실패 | 서버 상태 변경 없이 오류 표시 |
| 429 요청 제한 | Retry-After와 제한된 재시도 적용 |
| 네트워크/5xx | outbox 유지, 지연 재시도, 사용자가 취소 가능 |

## 인수 시험: 구현 후 실제 서버에서 통과해야 할 항목

1. A의 메모·이미지를 B/미로그인이 ID·URL을 알아도 읽거나 바꾸지 못한다.
2. 요청 owner_id·user_metadata를 바꿔도 서버 소유자가 바뀌지 않는다.
3. 로그인만 한 상태에서 기존 로컬 메모의 네트워크 전송이 없다.
4. 같은 작업을 전송 후 응답을 잃고 재전송해도 문서 리비전은 한 번만 증가한다.
5. 같은 operation_id에 다른 문서를 보내면 거절하며 타인 작업 존재 여부를 노출하지 않는다.
6. PC와 웹이 같은 기준에서 수정하면 한쪽이 충돌로 남고 양쪽 내용이 보존된다.
7. 업로드 도중 끊기거나 손상된 파일은 완료된 첨부로 기록하지 않는다.
8. 문서 업데이트와 첨부 연결·작업 영수증이 같은 원자적 경계에서 확정된다.
9. 오프라인 수정 후 앱을 종료·재시작해도 대기열과 원본이 남는다.
10. 계정 전환 때 A의 대기열이 B로 전송되지 않는다.
11. 로그아웃/인증 갱신 실패 후 업로드를 멈추고 로컬 편집·백업은 유지한다.
12. 휴지통 이동·다른 기기의 복구가 원본 이미지와 일관되게 동작한다.
13. 기기별 확대율·창 위치·펜 설정이 다른 기기의 값을 덮어쓰지 않는다.
14. 서비스 키·갱신 토큰이 로그·공개 저장소·브라우저 작업 파일·배포 ZIP에 없다.
15. 서버 커밋 순서 역전과 페이지 도중 변경이 생겨도 다음 동기화에서 누락을 복구한다. 검증 전 변경 커서 최적화는 도입하지 않는다.

설계 검토 목록이며 실제 서비스에서 실행한 시험 결과가 아니다. 현재 오프라인 왕복 검사는 사용자 간 클라우드 권한 검사를 대체하지 않는다.
